nsconv 0.1.0-rc1 · Octubre 2026

Kit de prueba de nsconv

Versión de prueba 0.1.0-rc1 de punta a punta: NetStream simulado, FlowLink y un PCE de prueba, con un paquete de evidencias.

Herramienta comunitaria no oficial. nsconv no es un producto de Illumio y no tiene soporte de Illumio. Se entrega tal cual ("as is"), sin garantía de ningún tipo (licencia MIT).

Resumen

nsconv recibe Huawei NetStream (NetFlow v5, v9 e IPFIX con particularidades de Huawei) y lo reexporta como IPFIX, NetFlow v9 o NetFlow v5 limpio hacia Illumio FlowLink. Este kit prueba la versión de prueba 0.1.0-rc1 de punta a punta en un laboratorio: un host de reproducción envía NetStream grabado o generado, nsconv lo convierte, FlowLink envía los flujos a un PCE de prueba y usted devuelve un archivo de evidencias por host. No se necesita un switch Huawei ni el PCE de producción.

#FlujoContenido
1Host de reproducción → nsconv, UDP 9996NetStream v5, v9 o IPFIX, origen 198.51.100.21:40000 (el switch de ejemplo; 40000 es el puerto de origen de exportación por defecto de Huawei1).
2nsconv → FlowLink, UDP 4739 (IPFIX) o 2055 (v9/v5)Registros limpios. Con source_address = "exporter" (por defecto) cada datagrama conserva como origen la IP y el puerto del switch, así FlowLink ve a los switches mismos.
3FlowLink → PCE de prueba, HTTPSResúmenes de flujos agregados, cada aggregation_minutes (por defecto 10, mínimo 5)2.

Qué necesita

  • Host nsconv: RHEL, Rocky o Alma Linux 8 x86_64 (9 también funciona), acceso root, tcpdump.
  • Host de reproducción: cualquier VM Linux en el mismo segmento de capa 2 que el host nsconv, con Python 3 y tcpreplay (EPEL 8 y 9 incluyen tcpreplay 4.6.13).
  • FlowLink 2.0.1 en el host nsconv o en otro host del mismo segmento, asociado a un PCE de prueba (una API key de ese PCE).
  • Los tres archivos del kit: esta guía, nsconv-sample-pcap.py (escribe capturas de prueba de NetStream al estilo Huawei con datos sintéticos) y nsconv-collect-evidence.sh (reúne las evidencias).

Instalar y configurar el laboratorio

PASO 1 Instalar nsconv 0.1.0-rc1 en el host nsconv

Descargue el RPM y SHA256SUMS de la carpeta releases/0.1.0-rc1/ de github.com/roschereric/netstream-converter, verifíquelos e instale. La versión del RPM es 0.1.0~rc1 (RPM no admite “-” en una versión; la versión final 0.1.0 la actualiza).

HOST NSCONV
# Descargar (o guardar ambos archivos de la carpeta con un navegador)
BASE=https://github.com/roschereric/netstream-converter/raw/main/releases/0.1.0-rc1
curl -LO $BASE/nsconv-0.1.0~rc1-1.x86_64.rpm -LO $BASE/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS      # debe mostrar: nsconv-0.1.0~rc1-1.x86_64.rpm: OK
sudo dnf install ./nsconv-0.1.0~rc1-1.x86_64.rpm
nsconvctl version

El RPM instala /usr/bin/nsconvctl, la unidad nsconv.service (usuario nsconv, única capacidad CAP_NET_RAW), la configuración /etc/nsconv/nsconv.toml y un archivo sysctl que sube net.core.rmem_max a 8 MiB cuando es menor. El servicio todavía no arranca.

PASO 2 Configuración mínima de nsconv para el laboratorio

Los valores por defecto ya sirven para el laboratorio: entrada huawei en UDP 9996 y una salida IPFIX a 127.0.0.1:4739 enviada desde la dirección del switch (source_address = "exporter"). Solo hay que definir la lista de permitidos: por defecto está vacía, así que se descarta todo. nsconvctl config set conserva los comentarios, valida, escribe y recarga.

HOST NSCONV
# Permitir los switches de ejemplo (el host de reproducción envía con estas IP de origen)
sudo nsconvctl config set input.huawei.allow '["198.51.100.0/24"]'
# FlowLink en otro host: apuntar la salida hacia él (ejemplo 192.0.2.11)
sudo nsconvctl config set output.flowlink.target 192.0.2.11:4739
# Abrir el puerto de entrada al host de reproducción e iniciar el servicio
sudo firewall-cmd --permanent --add-port=9996/udp && sudo firewall-cmd --reload
sudo systemctl enable --now nsconv
sudo nsconvctl status
exporter o local
exporter (por defecto): FlowLink ve la IP de cada switch, por eso su remote_addrs lista las IP de los switches, igual que si los switches enviaran directo a FlowLink. FlowLink debe estar en el host nsconv o en el mismo segmento de capa 2. local: nsconv envía desde su propia dirección; remote_addrs es 127.0.0.1 (mismo host) o la IP del host nsconv. Se cambia con sudo nsconvctl config set output.flowlink.source_address local.
PASO 3 FlowLink contra el PCE de prueba

Instale FlowLink 2.0.1 según la guía de FlowLink, guarde la API key y el secreto del PCE de prueba en /etc/illumio-flowlink/api_info1 y use un consumer por protocolo. FlowLink no tiene puertos por defecto y escucha en los puertos que usted configura2. Nunca reutilice un puerto de FlowLink para la entrada de nsconv.

/etc/illumio-flowlink/config.yaml (HOST FLOWLINK)
pce_addr: test-pce.example.com:443          # ejemplo: su PCE DE PRUEBA
org_id: 1                                   # ejemplo: org del PCE de prueba (SaaS)
api_key: $cat /etc/illumio-flowlink/api_info
data_directory: /var/lib/illumio-flowlink/data
aggregation_minutes: 5                      # mínimo: los flujos llegan antes al PCE
consumers:
  - name: nsconv-ipfix                      # protocolo de salida de nsconv = "ipfix"
    parser:
      type: ipfix
    connectors:
      - type: udp
        properties:
          ports: '4739'
          remote_addrs: ['198.51.100.21', '198.51.100.22']   # modo exporter: IP de los switches
  - name: nsconv-netflow                    # protocol = "netflow9" o "netflow5"
    parser:
      type: netflow
    connectors:
      - type: udp
        properties:
          ports: '2055'
          remote_addrs: ['198.51.100.21', '198.51.100.22']

HOST FLOWLINK
sudo systemctl restart illumio-flowlink
sudo -u ilo-flowlink /usr/local/bin/illumio-flowlink-ctl status
ss -lunp | grep flowlink                  # 4739 y 2055 escuchando
# Solo con FlowLink en otro host: abrir sus puertos al host nsconv
sudo firewall-cmd --permanent --add-port=4739/udp --add-port=2055/udp && sudo firewall-cmd --reload

remote_addrs acepta IP individuales, no CIDR2. Con source_address = "local" use '127.0.0.1' (mismo host) o la IP del host nsconv (ejemplo '192.0.2.10'). En el PCE, las IP de los flujos aparecen en Illumination solo cuando pertenecen a workloads3: si las IP de ejemplo no aparecen, cree workloads no gestionados (unmanaged) para algunas de ellas en el PCE de prueba.

Modo debug y dónde mirar

nsconv

El nivel de log es la clave de configuración log.level (error, warn, info, debug); no hay una opción aparte. Al cambiarlo, el daemon recarga sin reiniciar. En debug, cada datagrama o flujo descartado, recortado o completado con un valor por defecto registra una línea por tipo de evento, como máximo 5 líneas cada 10 s por evento y exportador y 2000 líneas cada 10 s en total (“N similar suppressed”).

HOST NSCONV
sudo nsconvctl config set log.level debug      # volver con: ... log.level info
nsconvctl logs -f                             # seguir el journal de nsconv
nsconvctl logs --since 30m                     # o "2026-10-21 14:00"
sudo nsconvctl logs --recent 200               # el buffer en memoria del daemon
journalctl -u nsconv NSCONV_EXPORTER=198.51.100.21:40000 -o verbose   # un switch
sudo nsconvctl status --detail                 # salud, alertas, exportadores, salidas, contadores
sudo nsconvctl status --exporter 198.51.100.21  # un switch: muestreo, desfase, pérdida de secuencia
sudo nsconvctl --json status --detail          # lo mismo en JSON (accounting.unaccounted debe ser 0)
sudo nsconvctl tui --lang es                   # vista de pantalla completa, pestaña de alertas

Las advertencias tienen identificadores estables (sampling-default, restamped, no-template, seq-gap, collector-down, …). Se silencia una con sudo nsconvctl dismiss <id>; vuelve si su valor se duplica.

Colector de depuración y capturas en bruto

nsconvctl decode --listen es un colector pequeño que muestra cada flujo que recibe. Úselo en un puerto que FlowLink no use (ejemplo 9997).

HOST NSCONV
# a) Lo que envía el host de reproducción, antes de nsconv: reproducir al puerto 9997 en lugar de 9996
nsconvctl decode --listen 0.0.0.0:9997
# b) Lo que envía nsconv: agregar una segunda salida a /etc/nsconv/nsconv.toml y luego: sudo nsconvctl reload
#    [[output]]
#    name = "debug"
#    protocol = "ipfix"
#    target = "127.0.0.1:9997"
#    source_address = "local"
nsconvctl decode --listen 127.0.0.1:9997 --count 50
# c) Datagramas NetStream en bruto de un switch a un pcap (usa tcpdump; por defecto 60 s / 2000 datagramas)
sudo nsconvctl debug-capture 198.51.100.21 --secs 120
# d) Decodificar cualquier captura sin conexión
nsconvctl decode nsconv-capture-198.51.100.21-*.pcap

FlowLink

FlowLink escribe sus logs en /var/log/illumio-flowlink/. Para una salida detallada, detenga el servicio e inícielo en modo verbose como ilo-flowlink1; la salida de debug muestra los registros entrantes, la IP, el puerto y el protocolo de cada registro, cada agregación y envío, y el código de respuesta del PCE2. Úselo solo durante la prueba y luego vuelva al servicio.

HOST FLOWLINK
sudo -u ilo-flowlink /usr/local/bin/illumio-flowlink-ctl stop
sudo -u ilo-flowlink /usr/local/bin/illumio-flowlink-ctl start -v
sudo tail -f /var/log/illumio-flowlink/flowlink.log
# después de la prueba
sudo -u ilo-flowlink /usr/local/bin/illumio-flowlink-ctl stop && sudo systemctl start illumio-flowlink

Simular NetStream

Generar una captura de prueba

nsconv-sample-pcap.py escribe un pcap de datagramas NetStream al estilo Huawei: NetFlow v5 (registros de 48 bytes), v9 (formato de plantilla de flujos originales de Huawei, con el campo privado 232 de Huawei) o IPFIX (tiempos relativos más el IE 160 en cada registro, campos enterprise de Huawei), puerto UDP de origen 40000, plantillas en datagramas propios antes de los datos y repetidas cada 10 datagramas de datos. Solo necesita Python 3.6 o posterior (RHEL 8: /usr/libexec/platform-python). Todos los valores son sintéticos.

HOST DE REPRODUCCIÓN
curl -LO https://roschereric.github.io/netstream-converter/test-kit/nsconv-sample-pcap.py
# MAC de la NIC del host nsconv (ejecutar en el host nsconv): ip -br link show <nic>
python3 nsconv-sample-pcap.py --version 9 --switch 198.51.100.21 --dst 192.0.2.10 \
    --dst-mac 52:54:00:12:34:56 --flows 200 --out v9.pcap --expect v9.expect.jsonl
OpciónSignificado (por defecto)
--version 5|9|ipfixVersión de exportación (9).
--switch IP[,IP…]Dirección(es) de origen del switch; cada switch recibe sus propios flujos (198.51.100.21).
--sport / --dst / --dportPuerto de origen del switch (40000), IP del host nsconv (192.0.2.10), puerto de entrada de nsconv (9996).
--dst-mac / --src-macMAC de las tramas. Para tcpreplay, --dst-mac debe ser la NIC de nsconv.
--src / --dst-hosts / --dst-portsIP o CIDR de workloads y puertos (10.1.1.0/24 → 10.2.2.0/24, puertos 443,22,3306,8080,53; IPv6: 2001:db8:a::/112 → 2001:db8:b::/112).
--flows N / --ipv6Flujos por switch (200) / workloads IPv6 (solo v9 e IPFIX).
--sampling NTasa 1 de N escrita como IE 34 en cada registro v9/IPFIX (0 = no informada, como hacen muchos switches Huawei).
--domain NSource ID v9 / Observation Domain IPFIX / engine id v5 (0): un segundo valor emula una segunda tarjeta de línea.
--pps / --template-every / --data-onlyTasa de datagramas en los tiempos del pcap (100); repetición de plantilla (10); datos sin plantillas (prueba de reinicio).
--expect FILE / --checkEscribir los flujos generados como líneas JSON / decodificar el pcap con nsconvctl y comparar cada flujo.
Genere justo antes de reproducir
Los tiempos de los flujos se fijan al generar (terminan entre 1 y 30 s antes). Un pcap reproducido más de 5 minutos después queda fuera de convert.max_clock_skew_secs = 300: nsconv desplaza entonces los tiempos al momento de recepción y cuenta restamped. Mantenga sincronizados los relojes de todos los hosts (chrony).

Opción A: nsconvctl replay (simple)

Envía el contenido NetStream de una captura con un socket UDP normal. Nunca falsifica el origen: nsconv y FlowLink ven la dirección del host de reproducción (ejemplo 192.0.2.20) y un puerto de origen efímero. Sirve para una primera prueba; para las pruebas de identidad del switch use la opción B.

HOST DE REPRODUCCIÓN Y HOST NSCONV
# host nsconv: permitir el host de reproducción; remote_addrs de FlowLink lista entonces 192.0.2.20 (modo exporter)
sudo nsconvctl config set input.huawei.allow '["198.51.100.0/24", "192.0.2.20"]'
# host de reproducción: copiar nsconvctl del RPM o el binario de la versión, luego
nsconvctl replay v9.pcap --to 192.0.2.10:9996 --rate 200

Opción B: tcpreplay (conserva la dirección de origen del switch)

tcpreplay envía las tramas tal como están en el pcap, así los datagramas llegan desde 198.51.100.21:40000: la lista de permitidos, la vista por switch y source_address = "exporter" se comportan como con un switch real. El generador ya escribe el destino correcto; cualquier otra captura (por ejemplo una de debug-capture, que es una captura Linux “cooked”) se reescribe antes con tcprewrite.

HOST DE REPRODUCCIÓN
sudo dnf install epel-release && sudo dnf install tcpreplay   # Rocky/Alma; RHEL: habilitar EPEL antes
# Solo para capturas que no vienen del generador: IP del colector anterior (ejemplo 192.0.2.50) hacia el
# host nsconv, su MAC, checksums recalculados. Agregue --dlt=enet para una captura cooked (debug-capture).
tcprewrite --infile=capture.pcap --outfile=lab.pcap \
    --enet-dmac=52:54:00:12:34:56 --enet-smac=02:00:00:00:00:01 \
    --dstipmap=192.0.2.50/32:192.0.2.10/32 --fixcsum
# Reproducir por la NIC que da al host nsconv
sudo tcpreplay --intf1=eth0 v9.pcap                         # tiempos del pcap (100 datagramas/s)
sudo tcpreplay --intf1=eth0 --pps=2000 --loop=30 burst.pcap   # prueba de carga
Opción de tcpreplay / tcprewriteEfecto (manual oficial)
--intf1 (-i)Interfaz de salida; obligatoria.
--pps / --mbps / --topspeedPaquetes por segundo / Mbps / lo más rápido posible; por defecto, los tiempos del pcap.
--loop / --duration / --limitRepetir el archivo N veces / parar tras N segundos / tras N paquetes.
--dstipmap (-D)Pseudo-NAT de las IP de destino, pares CIDR:CIDR.
--enet-dmac / --enet-smacReemplazar la MAC de destino / de origen.
--dlt=enetConvertir una captura Linux cooked a Ethernet (requiere ambas MAC).
--fixcsum (-C)Recalcular los checksums IPv4/TCP/UDP.

No use --unique-ip: cambia la cabecera IP (la dirección del switch), no las direcciones dentro de los registros NetStream.

Reproduzca desde otro host, nunca desde el host nsconv
tcpreplay escribe las tramas directamente en el lado de transmisión de la NIC. La pila de red del host nunca recibe lo que él mismo transmite, y el switch no devuelve una trama por el mismo puerto por el que llegó, así que una reproducción en el propio host nsconv nunca llega a nsconv. Use una segunda VM o host en el mismo segmento de capa 2 (misma VLAN, sin router en medio).

Verificaciones de red en el host nsconv

  • Filtro de ruta inversa: el valor por defecto de RHEL rp_filter = 1 (estricto) descarta un datagrama cuyo origen (198.51.100.21) se enrutaría de vuelta por otra interfaz. La ruta por defecto por la NIC receptora pasa. Si el host nsconv tiene varias NIC, agregue una ruta para el rango de los switches por la NIC receptora o use el modo flexible en ella: sudo sysctl -w net.ipv4.conf.<nic>.rp_filter=2. Los descartes aparecen en nstat -az TcpExtIPReversePathFilter, no en nsconv.
  • firewalld: UDP 9996 abierto en la zona de la NIC receptora (paso 2).
  • Lista de permitidos: input.huawei.allow contiene el rango de los switches (opción B) o la IP del host de reproducción (opción A); el resto se cuenta como denied.
  • Verificar la llegada: sudo tcpdump -ni any udp port 9996 -c 5 y luego sudo nsconvctl status.

Respuestas que buscamos
Las pruebas 6–11 y 18 muestran cómo trata FlowLink 2.0.1 los orígenes con IP de switch desde un relay en el mismo host, los dominios de tarjetas de línea, la tasa de muestreo, los contadores de bytes (IE 1 u 85), IPv6 y los intervalos de tiempo. Reunir las evidencias

nsconv-collect-evidence.sh se ejecuta como root durante una ventana de tiempo (por defecto 300 s). Captura con tcpdump la entrada NetStream (switch → nsconv) y cada salida de nsconv (nsconv → colector), cada archivo con un tope de 100 MB, y reúne todo lo necesario para verificar la prueba. No cambia nada en el host; una herramienta o un archivo que falte queda registrado y la ejecución sigue.

HOST NSCONV
curl -LO https://roschereric.github.io/netstream-converter/test-kit/nsconv-collect-evidence.sh
sudo bash nsconv-collect-evidence.sh --dry-run             # muestra lo que va a ejecutar
sudo bash nsconv-collect-evidence.sh --secs 300 --sample v9.pcap --note "pruebas 2, 6: v9, dos switches"
# ahora inicie la reproducción en el host de reproducción; debe terminar dentro de la ventana

Cómo se validan las evidencias

Una prueba es correcta cuando todos los puntos siguientes se cumplen en su ventana. Las verificaciones usan solo lo que contiene el .tgz.

  • Entrada = generado — los flujos de pcap/input.flows.jsonl son iguales a los flujos generados (archivo --expect, o el pcap de muestra decodificado otra vez).
  • Salida = entrada — pcap/output-<nombre>.flows.jsonl contiene los mismos flujos (direcciones, puertos, protocolo, paquetes, bytes, tiempos), cada uno exactamente una vez, con la IP y el puerto del switch como exportador en modo exporter.
  • Nada sin contabilizar — en nsconv-status-after.json, accounting.unaccounted es 0, la diferencia de flows_in y flows_out entre antes y después es igual a los flujos reproducidos, denied, malformed y send_errors no crecieron, y RcvbufErrors en udp-snmp no cambió.
  • FlowLink aceptó los switches — files/flowlink-window.log nombra las IP de los switches (o 127.0.0.1 / el host nsconv en modo local) y no muestra descartes ni “bad data” para ellas.
  • El PCE los recibió — el mismo log muestra los envíos al PCE de prueba con éxito (con el código de respuesta del PCE en modo verbose), y Explorer muestra los flujos de workloads de la prueba (su nota).
  • Host limpio — ninguna denegación AVC, servicio activo, ningún reinicio durante la ventana (NRestarts).

Anexo: autoverificación del generador

--check decodifica el pcap generado con nsconvctl decode --json y compara cada flujo (exportador, direcciones, puertos, protocolo, paquetes, bytes, tiempos de inicio y fin, tasa de muestreo) con lo generado. Ejecútelo en el host nsconv antes de una prueba.

HOST NSCONV
/usr/libexec/platform-python nsconv-sample-pcap.py --version ipfix --ipv6 --sampling 2048 --out t.pcap --check
# check OK: nsconvctl decoded 200 of 200 flows with identical addresses, ports, protocol, packets, bytes and times

Antes de esta versión se generaron y decodificaron sin diferencias diez variantes (v5; v5 con un segundo engine id; v9 e IPFIX, cada una IPv4 e IPv6, con y sin tasa de muestreo informada; dos switches cada una, 666 flujos por archivo), en macOS y en Rocky Linux 8.10 con platform-python 3.6. En Rocky 8.10, las tramas también se reprodujeron con la dirección de origen del switch hacia nsconv (modo exporter): las capturas de entrada y salida del script de evidencias contenían los mismos 500 flujos, unaccounted fue 0 y, después de un reinicio, una captura de solo datos se decodificó con las plantillas restauradas.
