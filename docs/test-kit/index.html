nsconv 0.1.0-rc1 · October 2026

nsconv Test Kit

Test release 0.1.0-rc1 end to end: simulated NetStream, FlowLink and a test PCE, with an evidence bundle.

Unofficial community tool. nsconv is not an Illumio product and is not supported by Illumio. Provided as is, without warranty of any kind (MIT licence).

Overview

nsconv receives Huawei NetStream (NetFlow v5, v9 and IPFIX with Huawei specifics) and re-exports clean IPFIX, NetFlow v9 or NetFlow v5 to Illumio FlowLink. This kit tests the test release 0.1.0-rc1 end to end in a lab: a replay host plays recorded or generated NetStream, nsconv converts it, FlowLink sends the flows to a test PCE, and you send back one evidence file per host. No Huawei switch and no production PCE are needed.

#FlowContent
1Replay host → nsconv, UDP 9996NetStream v5, v9 or IPFIX, source 198.51.100.21:40000 (the example switch; 40000 is Huawei's default export source port1).
2nsconv → FlowLink, UDP 4739 (IPFIX) or 2055 (v9/v5)Clean records. With source_address = "exporter" (default) each datagram keeps the switch IP and port as its source, so FlowLink sees the switches themselves.
3FlowLink → test PCE, HTTPSAggregated flow summaries, every aggregation_minutes (default 10, minimum 5)2.

What you need

  • nsconv host: RHEL, Rocky or Alma Linux 8 x86_64 (9 also works), root access, tcpdump.
  • Replay host: any Linux VM on the same Layer 2 segment as the nsconv host, with Python 3 and tcpreplay (EPEL 8 and 9 ship tcpreplay 4.6.13).
  • FlowLink 2.0.1 on the nsconv host or on a separate host of the same segment, paired with a test PCE (an API key of that PCE).
  • The three kit files: this guide, nsconv-sample-pcap.py (writes Huawei-style NetStream test captures with synthetic data) and nsconv-collect-evidence.sh (collects the evidence).

Install and configure the lab

STEP 1 Install nsconv 0.1.0-rc1 on the nsconv host

Download the RPM and SHA256SUMS from the releases/0.1.0-rc1/ folder of github.com/roschereric/netstream-converter, check them, and install. The RPM version is 0.1.0~rc1 (RPM cannot use “-” in a version; the final 0.1.0 upgrades it).

NSCONV HOST
# Download (or save both files from the folder in a browser)
BASE=https://github.com/roschereric/netstream-converter/raw/main/releases/0.1.0-rc1
curl -LO $BASE/nsconv-0.1.0~rc1-1.x86_64.rpm -LO $BASE/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS      # must print: nsconv-0.1.0~rc1-1.x86_64.rpm: OK
sudo dnf install ./nsconv-0.1.0~rc1-1.x86_64.rpm
nsconvctl version

The RPM installs /usr/bin/nsconvctl, the unit nsconv.service (user nsconv, only capability CAP_NET_RAW), the config /etc/nsconv/nsconv.toml and a sysctl file that raises net.core.rmem_max to 8 MiB when it is lower. The service is not started yet.

STEP 2 Minimal nsconv configuration for the lab

The defaults already fit the lab: input huawei on UDP 9996, one IPFIX output to 127.0.0.1:4739 sent from the switch address (source_address = "exporter"). Only the allow-list must be set: it is empty by default, so everything is dropped. nsconvctl config set keeps the comments, validates, writes and reloads.

NSCONV HOST
# Allow the example switches (the replay host sends with these source IPs)
sudo nsconvctl config set input.huawei.allow '["198.51.100.0/24"]'
# FlowLink on a separate host: point the output at it (example 192.0.2.11)
sudo nsconvctl config set output.flowlink.target 192.0.2.11:4739
# Open the input port to the replay host, start the service
sudo firewall-cmd --permanent --add-port=9996/udp && sudo firewall-cmd --reload
sudo systemctl enable --now nsconv
sudo nsconvctl status
exporter or local
exporter (default): FlowLink sees each switch IP, so its remote_addrs lists the switch IPs, exactly as if the switches sent to FlowLink directly. FlowLink must be on the nsconv host or on the same Layer 2 segment. local: nsconv sends from its own address; remote_addrs is 127.0.0.1 (same host) or the nsconv host IP. Switch with sudo nsconvctl config set output.flowlink.source_address local.
STEP 3 FlowLink against the test PCE

Install FlowLink 2.0.1 as described in the FlowLink guide, store the test PCE API key and secret in /etc/illumio-flowlink/api_info1, and use one consumer per protocol. FlowLink has no default ports and listens on the ports you configure2. Never reuse a FlowLink port for the nsconv input.

/etc/illumio-flowlink/config.yaml (FLOWLINK HOST)
pce_addr: test-pce.example.com:443          # example: your TEST PCE
org_id: 1                                   # example: org of the test PCE (SaaS)
api_key: $cat /etc/illumio-flowlink/api_info
data_directory: /var/lib/illumio-flowlink/data
aggregation_minutes: 5                      # minimum: flows reach the PCE sooner
consumers:
  - name: nsconv-ipfix                      # nsconv output protocol = "ipfix"
    parser:
      type: ipfix
    connectors:
      - type: udp
        properties:
          ports: '4739'
          remote_addrs: ['198.51.100.21', '198.51.100.22']   # exporter mode: the switch IPs
  - name: nsconv-netflow                    # protocol = "netflow9" or "netflow5"
    parser:
      type: netflow
    connectors:
      - type: udp
        properties:
          ports: '2055'
          remote_addrs: ['198.51.100.21', '198.51.100.22']

FLOWLINK HOST
sudo systemctl restart illumio-flowlink
sudo -u ilo-flowlink /usr/local/bin/illumio-flowlink-ctl status
ss -lunp | grep flowlink                  # 4739 and 2055 listening
# Separate FlowLink host only: open its ports to the nsconv host
sudo firewall-cmd --permanent --add-port=4739/udp --add-port=2055/udp && sudo firewall-cmd --reload

remote_addrs takes single IPs, not CIDRs2. With source_address = "local" use '127.0.0.1' (same host) or the nsconv host IP (example '192.0.2.10'). In the PCE, flow IPs show in Illumination only when they belong to workloads3: if the example workload IPs do not appear, create unmanaged workloads for a few of them in the test PCE.

Debug mode and where to look

nsconv

The log level is the config key log.level (error, warn, info, debug); there is no separate flag. Changing it reloads the daemon without a restart. At debug, every dropped, clamped or defaulted datagram or flow logs one line per event kind, at most 5 lines per 10 s per event and exporter and 2000 lines per 10 s in total (“N similar suppressed”).

NSCONV HOST
sudo nsconvctl config set log.level debug      # back with: ... log.level info
nsconvctl logs -f                             # follow the journal of nsconv
nsconvctl logs --since 30m                     # or "2026-10-21 14:00"
sudo nsconvctl logs --recent 200               # the daemon's in-memory ring
journalctl -u nsconv NSCONV_EXPORTER=198.51.100.21:40000 -o verbose   # one switch
sudo nsconvctl status --detail                 # health, alerts, exporters, outputs, counters
sudo nsconvctl status --exporter 198.51.100.21  # one switch: sampling, skew, sequence loss
sudo nsconvctl --json status --detail          # the same as JSON (accounting.unaccounted must be 0)
sudo nsconvctl tui                             # full-screen view, Alerts tab; --lang es

Warnings have stable ids (sampling-default, restamped, no-template, seq-gap, collector-down, …). Silence one with sudo nsconvctl dismiss <id>; it returns if its value doubles.

Debug collector and raw captures

nsconvctl decode --listen is a small collector that prints every flow it receives. Use it on a port that FlowLink does not use (example 9997).

NSCONV HOST
# a) What the replay host sends, before nsconv: replay to port 9997 instead of 9996
nsconvctl decode --listen 0.0.0.0:9997
# b) What nsconv sends: add a second output to /etc/nsconv/nsconv.toml, then: sudo nsconvctl reload
#    [[output]]
#    name = "debug"
#    protocol = "ipfix"
#    target = "127.0.0.1:9997"
#    source_address = "local"
nsconvctl decode --listen 127.0.0.1:9997 --count 50
# c) Raw NetStream datagrams of one switch into a pcap (runs tcpdump, default 60 s / 2000 datagrams)
sudo nsconvctl debug-capture 198.51.100.21 --secs 120
# d) Decode any capture offline
nsconvctl decode nsconv-capture-198.51.100.21-*.pcap

FlowLink

FlowLink logs to /var/log/illumio-flowlink/. For verbose output, stop the service and start it in verbose mode as ilo-flowlink1; debug output shows incoming records, the IP, port and protocol of each record, every aggregation and upload, and the PCE response code2. Use it only during the test, then return to the service.

FLOWLINK HOST
sudo -u ilo-flowlink /usr/local/bin/illumio-flowlink-ctl stop
sudo -u ilo-flowlink /usr/local/bin/illumio-flowlink-ctl start -v
sudo tail -f /var/log/illumio-flowlink/flowlink.log
# after the test
sudo -u ilo-flowlink /usr/local/bin/illumio-flowlink-ctl stop && sudo systemctl start illumio-flowlink

Simulate NetStream

Generate a test capture

nsconv-sample-pcap.py writes a pcap of Huawei-style NetStream datagrams: NetFlow v5 (48-byte records), v9 (Huawei original-flow template layout, with the Huawei private field 232) or IPFIX (relative times plus IE 160 in every record, Huawei enterprise fields), UDP source port 40000, templates in their own datagrams before the data and repeated every 10 data datagrams. It needs only Python 3.6 or later (RHEL 8: /usr/libexec/platform-python). All values are synthetic.

REPLAY HOST
curl -LO https://roschereric.github.io/netstream-converter/test-kit/nsconv-sample-pcap.py
# MAC of the nsconv host NIC (run on the nsconv host): ip -br link show <nic>
python3 nsconv-sample-pcap.py --version 9 --switch 198.51.100.21 --dst 192.0.2.10 \
    --dst-mac 52:54:00:12:34:56 --flows 200 --out v9.pcap --expect v9.expect.jsonl
OptionMeaning (default)
--version 5|9|ipfixExport version (9).
--switch IP[,IP…]Switch source address(es); each switch gets its own flows (198.51.100.21).
--sport / --dst / --dportSwitch source port (40000), nsconv host IP (192.0.2.10), nsconv input port (9996).
--dst-mac / --src-macFrame MACs. --dst-mac must be the nsconv NIC for tcpreplay.
--src / --dst-hosts / --dst-portsWorkload IPs or CIDRs and ports (10.1.1.0/24 → 10.2.2.0/24, ports 443,22,3306,8080,53; IPv6: 2001:db8:a::/112 → 2001:db8:b::/112).
--flows N / --ipv6Flows per switch (200) / IPv6 workloads (v9 and IPFIX only).
--sampling N1-in-N rate written as IE 34 in every v9/IPFIX record (0 = not reported, as many Huawei switches do).
--domain Nv9 Source ID / IPFIX Observation Domain / v5 engine id (0): a second value emulates a second line card.
--pps / --template-every / --data-onlyDatagram rate in the pcap timestamps (100); template repeat (10); data without templates (restart test).
--expect FILE / --checkWrite the generated flows as JSON lines / decode the pcap with nsconvctl and compare every flow.
Generate just before you replay
Flow times are set at generation time (they end 1 to 30 s before it). A pcap replayed more than 5 minutes later is outside convert.max_clock_skew_secs = 300: nsconv then shifts the times to the receive time and counts restamped. Keep the clocks of all hosts synchronized (chrony).

Option A: nsconvctl replay (simple)

Sends the NetStream payloads of a capture with a normal UDP socket. It never spoofs: nsconv and FlowLink see the replay host address (example 192.0.2.20) and an ephemeral source port. Good for a first check; for the switch identity tests use option B.

REPLAY HOST AND NSCONV HOST
# nsconv host: allow the replay host; FlowLink remote_addrs then lists 192.0.2.20 (exporter mode)
sudo nsconvctl config set input.huawei.allow '["198.51.100.0/24", "192.0.2.20"]'
# replay host: copy nsconvctl from the RPM or the release binary, then
nsconvctl replay v9.pcap --to 192.0.2.10:9996 --rate 200

Option B: tcpreplay (keeps the switch source address)

tcpreplay sends the frames exactly as they are in the pcap, so the datagrams arrive from 198.51.100.21:40000: the allow-list, the per-switch view and source_address = "exporter" behave as with a real switch. The generator already writes the right destination; for any other capture (for example one taken with debug-capture, which is a Linux “cooked” capture) rewrite it first with tcprewrite.

REPLAY HOST
sudo dnf install epel-release && sudo dnf install tcpreplay   # Rocky/Alma; RHEL: enable EPEL first
# Only for captures not made by the generator: old collector IP (example 192.0.2.50) to the
# nsconv host, its MAC, recalculated checksums. Add --dlt=enet for a cooked capture (debug-capture).
tcprewrite --infile=capture.pcap --outfile=lab.pcap \
    --enet-dmac=52:54:00:12:34:56 --enet-smac=02:00:00:00:00:01 \
    --dstipmap=192.0.2.50/32:192.0.2.10/32 --fixcsum
# Replay on the NIC that faces the nsconv host
sudo tcpreplay --intf1=eth0 v9.pcap                         # pcap timing (100 datagrams/s)
sudo tcpreplay --intf1=eth0 --pps=2000 --loop=30 burst.pcap   # load test
tcpreplay / tcprewrite optionEffect (official manual)
--intf1 (-i)Output interface; required.
--pps / --mbps / --topspeedPackets per second / Mbps / as fast as possible; default is the pcap timing.
--loop / --duration / --limitRepeat the file N times / stop after N seconds / after N packets.
--dstipmap (-D)Pseudo-NAT of destination IPs, CIDR:CIDR pairs.
--enet-dmac / --enet-smacOverride destination / source MAC.
--dlt=enetConvert a Linux cooked capture to Ethernet (needs both MACs).
--fixcsum (-C)Recalculate IPv4/TCP/UDP checksums.

Do not use --unique-ip: it changes the IP header (the switch address), not the addresses inside the NetStream records.

Replay from a separate host, never from the nsconv host
tcpreplay writes frames straight to the NIC’s transmit side. The host’s own network stack never receives what it transmits, and the switch port does not send a frame back out of the port it came from, so a replay on the nsconv host itself never reaches nsconv. Use a second VM or host on the same Layer 2 segment (same VLAN, no router in between).

Network checks on the nsconv host

  • Reverse-path filter: RHEL’s default rp_filter = 1 (strict) drops a datagram whose source (198.51.100.21) would be routed back through a different interface. The default route through the receiving NIC passes. If the nsconv host has several NICs, add a route for the switch range through the receiving NIC, or set loose mode on it: sudo sysctl -w net.ipv4.conf.<nic>.rp_filter=2. Dropped datagrams show in nstat -az TcpExtIPReversePathFilter, not in nsconv.
  • firewalld: UDP 9996 open on the zone of the receiving NIC (step 2).
  • Allow-list: input.huawei.allow holds the switch range (option B) or the replay host IP (option A); others count as denied.
  • Check arrival: sudo tcpdump -ni any udp port 9996 -c 5, then sudo nsconvctl status.

Collect the evidence

nsconv-collect-evidence.sh runs as root for a time window (default 300 s). It captures the NetStream input (switch → nsconv) and every nsconv output (nsconv → collector) with tcpdump, each file capped at 100 MB, and collects everything needed to check the run. Nothing on the host is changed; a missing tool or file is recorded and the run goes on.

NSCONV HOST
curl -LO https://roschereric.github.io/netstream-converter/test-kit/nsconv-collect-evidence.sh
sudo bash nsconv-collect-evidence.sh --dry-run             # shows what it will run
sudo bash nsconv-collect-evidence.sh --secs 300 --sample v9.pcap --note "tests 2, 6: v9, two switches"
# now start the replay on the replay host; it must finish inside the window
# FlowLink on a separate host: run there at the same time
sudo bash nsconv-collect-evidence.sh --flowlink-only --secs 300
In the .tgzContent
pcap/input.pcap, output-<name>.pcap (FlowLink host: flowlink-input.pcap), each decoded by nsconvctl decode into .flows.jsonl
cmd/nsconvctl version, status --json --detail before and after, logs --since, journal (JSON), config show, unit status, systemd-analyze security, rp_filter and buffer sysctls, firewalld, nftables, SELinux and AVC denials, ss -lunp, ip addr/route, clock (chrony), FlowLink version, service and illumio-flowlink-ctl status
files/nsconv.toml, FlowLink config.yaml with secrets replaced by <REDACTED>, the FlowLink log lines of the window, FlowLink’s config schema, your sample pcaps
MANIFEST.tsv, SHA256SUMS, SUMMARY.txt, NOTE.txtEvery item with its exit code and SHA-256; checksums for sha256sum -c; flows per capture and unaccounted; your note
Send it back
The script prints the file name nsconv-evidence-<host>-<UTC time>.tgz and its SHA-256. Send the .tgz (and the one from the FlowLink host, if separate) with the SHA-256 and your notes through your usual channel to your contact for this test. The FlowLink API key file is never read, and API keys, secrets, tokens and passwords in config.yaml are replaced; the captures contain only the synthetic test flows.

How the evidence is validated

A test passes when every step below holds for its window. The checks use only what is inside the .tgz.

  • Input = generated — the flows in pcap/input.flows.jsonl equal the generated flows (--expect file, or the sample pcap decoded again).
  • Output = input — pcap/output-<name>.flows.jsonl holds the same flows (addresses, ports, protocol, packets, bytes, times), each exactly once, with the switch IP and port as exporter in exporter mode.
  • Nothing unaccounted — in nsconv-status-after.json, accounting.unaccounted is 0, the difference of flows_in and flows_out before and after equals the replayed flows, denied, malformed and send_errors did not grow, and RcvbufErrors in udp-snmp did not change.
  • FlowLink accepted the switches — files/flowlink-window.log names the switch IPs (or 127.0.0.1 / the nsconv host in local mode) and shows no discard or “bad data” for them.
  • The PCE received them — the same log shows the uploads to the test PCE succeeding (with the PCE response code in verbose mode), and Explorer shows the workload flows of the test (your note).
  • Host clean — no AVC denial, service active, no restart during the window (NRestarts).
Sources
  1. [nsconv] status schema nsconv.status/1: accounting equations and the unaccounted residual, shown by nsconvctl status.

Appendix: generator self-check

--check decodes the generated pcap with nsconvctl decode --json and compares every flow (exporter, addresses, ports, protocol, packets, bytes, start and end time, sampling rate) with what was generated. Run it on the nsconv host before a test.

NSCONV HOST
